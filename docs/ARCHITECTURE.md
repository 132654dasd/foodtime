# 架构说明

## 一、整体形态

```
┌──────────────────────────────┐        ┌────────────────────────────────────┐
│  浏览器 (Vue 3 SPA)          │        │  Spring Boot 4 应用                │
│  Element Plus + Pinia        │  HTTP  │                                    │
│  axios → /api/**             │ ─────► │  TraceIdFilter                     │
│  Vite dev server :5173       │  JSON  │    ↓                               │
│  （生产由后端托管静态产物）   │        │  JwtAuthenticationFilter           │
└──────────────────────────────┘        │    ↓                               │
                                        │  RateLimitAspect (@RateLimit)      │
                                        │    ↓                               │
                                        │  Controller → Service → Repository │
                                        │    ↓            ↓                  │
                                        │  Caffeine     JPA / Hibernate      │
                                        └────────────────┬───────────────────┘
                                                         ↓
                                                   MySQL 8.0
```

**为什么前后端分离**：核心交互（随机配餐的抽卡动画、社区无限滚动、图片上传预览）
天然是富客户端场景；服务端渲染要额外引入模板与局部刷新技术，收益反而更低。

**生产形态**：`npm run build` 的产物由 Spring Boot 静态托管，最终只有**一个 jar**。
开发期才需要两个进程。

## 二、后端分层

```
Controller   只做 HTTP 语义：参数绑定、校验、把 Service 结果包成统一响应体
    ↓        不写业务判断，不碰 Entity
Service      事务边界、业务规则、权限校验、缓存注解、Entity ↔ VO 转换
    ↓
Repository   Spring Data JPA；复杂查询用 @Query，MySQL 专有语法用 nativeQuery
    ↓
Entity       只描述表结构与关联，不承载业务方法
```

### 几条贯穿全局的约定

**1. Entity 永不直接返回给前端。**
响应一律走 `record` 形式的 VO。`SysUser` 携带 BCrypt 哈希，
只要实体不直接序列化，就不存在"忘了加 `@JsonIgnore` 导致密码哈希泄漏"的风险。
这是把安全做成结构性保证，而不是靠自觉。

**2. 统一响应体 `{ code, message, data, traceId }`。**
`code` 复用 HTTP 语义，前端可以统一拦截处理。
`traceId` 让"用户截图报错 → 后端精确定位日志"成为一条命令的事。

**3. 异常分两类。**
业务预期内的失败抛 `BizException`（带 `ErrorCode`），由 `GlobalExceptionHandler` 翻译成 4xx；
其余异常一律兜底成 500，**并且不把堆栈返回给前端**。
日志策略也分开：4xx 记一行 WARN（不打堆栈，否则日志会被刷爆），5xx 记完整堆栈。

**4. 权限在后端强制。**
前端隐藏按钮只是体验优化。菜谱的写操作在 `SecurityConfig` 里限定 `hasRole('ADMIN')`，
方法上再挂一层 `@PreAuthorize` 作为双保险——万一将来有人改动了 URL 规则，方法级注解仍然拦得住。
实测普通用户直接构造 `POST /api/recipes` 得到 **403**。

## 三、数据模型要点

15 张表，核心关系：

```
sys_user ──1:N── user_avoidance        用户忌口关键词
    │
    ├──1:N── community_post ──1:N── post_image
    │            ├──1:N── post_like       （uk: post_id + user_id）
    │            └──1:N── post_comment    （自关联 parent_id，只两级）
    │
    └──1:N── menu_history               配餐历史，用于"避免重复推荐"

recipe ──1:N── recipe_step              步骤（uk: recipe_id + step_no）
   │   ──1:N── recipe_ingredient        食材（idx: name，忌口反查用）
   │   ──N:M── recipe_tag               标签（含过敏原这类"看不出来"的信号）
   │   ──1:N── user_favorite            （uk: user_id + recipe_id）
   └   ──1:N── recipe_rating            （uk: user_id + recipe_id）
```

### 三个刻意的设计选择

**① 难度双列存储**：`difficulty`（枚举名，给人看）+ `difficulty_level`（1/2/3，给索引用）。
中文难度的字典序没有业务含义，排序必须走数值列。实测 `EXPLAIN` 命中覆盖索引。

**② 计数冗余存储 + 原子更新**：
`like_count`、`comment_count`、`view_count`、`favorite_count` 都是冗余列，
配合 `UPDATE ... SET col = col + ?` 使用。
好处是列表页不需要三个 `COUNT` 子查询；代价是必须保证所有变更路径都同步维护它。

**③ 唯一约束承担幂等，而不是应用层判断**：
`post_like(post_id, user_id)`、`user_favorite(user_id, recipe_id)` 上的唯一键，
让"重复点赞/重复收藏"在并发下天然幂等。
应用层的"先查再插"必然有竞态窗口，只有数据库能真正保证。

这里踩过一个坑：在同一个事务里捕获 `DataIntegrityViolationException`（唯一键冲突）后，
该事务已被标记为 rollback-only，后续任何操作都会失败。
解法是把插入拆到独立事务的小组件 `PostLikeWriter` 里（`REQUIRES_NEW`），
让"并发第二次插入失败"变成一个可预期的返回值，而不是污染外层事务。

## 四、随机配餐：核心算法的设计

这是整个项目里最值得讲的部分。

### 流程

```
规格校验 → 合并忌口 → 拉候选池(轻量投影) → 剔除忌口 → 去重近期 → 策略抽样 → 汇总 → 记历史
```

### 为什么忌口过滤这样实现

一个关键词会拉黑三类菜谱：**食材名**包含它、**标签**包含它、**菜名**包含它。
第三类容易被忽略，但用户说"不要香菜"时，`香菜拌牛肉` 显然也该排除；
第二类是兜底——像"花生""坚果""乳制品"这些过敏原，未必能从食材名直接看出来。

实现上**不做 SQL 层的动态拼接**，而是：
每个关键词单独查一次"被拉黑的 id 集合"，结果用 **Caffeine 按关键词缓存 30 分钟**，
再在 Java 侧取并集。

好处是：忌口关键词高度重复（"香菜""花生"会被大量用户用到），缓存后绝大多数配餐请求
**完全不碰 ingredient 表**；而且查询是普通 JPQL，H2 上也能测。

### 候选池为什么用轻量投影

`RecipeCandidate` 只含 6 个标量列（id/分类/耗时/难度/浏览/收藏），
不碰 steps/ingredients 关联。于是**一次查询就能把整个候选池读进内存**，
之后所有筛选与抽样都在 Java 侧完成，不需要反复回库。

### 三种策略与加权抽样

抽样用「**前缀和 + 二分查找**」实现不放回加权随机：把权重累加成单调数组，
取一个 `[0, total)` 的随机数二分定位。复杂度 O(k·n)，比反复重排整个池子稳定。

- **RANDOM**：等概率
- **BALANCED**：按分类**轮转**（荤→素→凉→主食→甜品），每轮各取一道。
  只要池里有素菜，就不会出现"十道全是肉"。同一分类内用**热度加权**（对数压缩，
  避免一道爆款菜长期霸占菜单）
- **QUICK**：权重 `1/(1+分钟/30)`。刻意**不**按耗时升序取前 N——
  那样会退化成"永远只推那几道最快的菜"，反而失去了"帮我决定"的意义

### 降级而不是报错

池子不足时不抛异常、也不假装配齐了，而是**按实际数量返回并在 `warnings` 里说明原因**
（缺哪类、补了什么）。前端必须把 `warnings` 展示给用户——
一个诚实的"汤池只剩 2 道"比一个静默缩水的菜单有用得多。

这个设计在测试中还救回了一个 bug：当用户只要汤（`dishCount=0`）时，
均衡策略原本会加一条"菜池里没有素菜可配"的噪声告警，
还会把真正重要的"汤不够"挤到后面。现在只在 `dishCount > 0` 时才检查素菜。

## 五、认证与授权

**JWT（HS256）无状态认证**，密钥启动时校验长度（HS256 硬性要求 ≥256 bit），
避免运行期才炸。令牌只携带 `uid` 与 `role`，不放用户名——用户名可能在库里被改。

**一个真实的安全缺口与它的补法**：
纯"只信 token 声明"的做法，在用户被禁用或删除后，旧 token 到期前依然畅通无阻。
但每个请求都查库又太贵。折中是把用户状态放进 **Caffeine 短 TTL 缓存（5 分钟）**：
绝大多数请求零数据库开销，禁用操作最多 5 分钟后生效；
而管理员的禁用/改密操作会主动 `@CacheEvict`，立即生效。

**防用户名枚举**：登录时如果用户名不存在，也会走一次**等价开销的哈希校验**，
抹平两条路径的响应耗时差；且"用户名不存在"与"密码错误"返回**完全相同**的提示。

**改密必须提供旧密码**：即使已持有有效 token，也不能凭一个可能被盗用的会话直接改掉密码。
测试里有对应用例。

## 六、错误处理与可观测

`TraceIdFilter` 优先级设为最高，保证后续所有日志（含 Security 过滤器链里的）都带 traceId。
客户端可通过 `X-Trace-Id` 透传；服务端会**清洗**这个值（限长、只留安全字符），
避免有人塞超长或含换行的值污染日志。

401/403 的响应体必须自己实现（`RestAuthenticationEntryPoint` / `RestAccessDeniedHandler`）——
Spring Security 默认返回 HTML 登录页或空响应，前后端分离下前端拿不到可解析的结构。
注意这两个在**过滤器链里**，走不到 `@RestControllerAdvice`。

## 七、前端结构（Vite + Vue 3）

```
src/
├── api/         axios 实例 + 按领域拆分的接口函数 + 全部 TS 类型
├── stores/      Pinia：用户会话（token 持久化）
├── router/      路由表，全部懒加载
├── components/  通用组件（RecipeCover 渐变封面、布局、空/加载态）
├── views/       页面
└── utils/
```

**封面占位是个关键细节**：种子菜谱的 `coverUrl` 全是 `null`。
前端用菜名的**确定性哈希**生成一组渐变色（同一菜名颜色恒定）并显示首字。
这样既保证离线可用、零网络依赖，又让整个菜品库视觉统一；
管理员上传真实封面后自动切换为图片。

## 八、已知的架构约束

| 约束 | 影响 | 演进方向 |
|---|---|---|
| 缓存为进程内 Caffeine | 多实例间不共享、无法统一失效 | 换 `CacheManager` 为 Redis，业务代码不改 |
| 图片存本地磁盘 | 多实例下需共享卷 | 换对象存储，上传接口已按"返回 URL"设计 |
| 浏览量内存计数 | 崩溃丢最近 30 秒 | 可接受的取舍；要精确就每次写库 |
| 无令牌黑名单 | 登出后旧 token 在有效期内仍可用 | 引入 Redis 黑名单或缩短 TTL |
| 单库单实例 | 无读写分离、无分库分表 | 当前数据量远未到瓶颈 |

## 九、做菜成本的建模与取舍

需求是「管理员维护蔬菜价格，用户选好菜后看到每道菜的价格和总费用」。
真正难的不是加法，而是**量纲统一**——菜谱写「2 个」，价目表写「元/斤」。

### 9.1 数据模型

价格独立成表 `ingredient_price`，以**食材名**为业务主键（唯一索引）：

- 为什么不把 `price` 加到 `recipe_ingredient`？因为价格是食材的**全局属性**。
  番茄出现在几十道菜里，价格挂在食材行上会变成「同一食材在不同菜里价格不同」，
  改价还要改几十行。
- `price_unit` 是计价单位，与菜谱里的用量单位**解耦**；
  `grams_per_unit` 存「1 个该计数单位约等于多少克」，供跨单位换算。

### 9.2 换算阶梯：一律先折成「克」

`UnitConverter` 不写 N×M 个分支，而是统一走一条阶梯：

```
重量 g / kg / 斤 / 两 ─┐
体积 ml / l            ├─→ 克 ─→ 目标计价单位
勺 1勺=15ml / 1小勺=5ml │
计数 个/根/片/…        ─┘（靠 grams_per_unit）
```

一条阶梯覆盖全部组合。中间结果保留 6 位小数，只对**最终金额**四舍五入到 2 位，
避免逐级舍入放大误差。

### 9.3 三处刻意的「不精确」，都摆在明面上

| 近似 | 做法 | 为什么可接受 / 如何兜底 |
|---|---|---|
| 体积 ↔ 重量按 1:1 | 1 ml 当 1 g | 调料密度接近水，误差在「几厘钱」量级 |
| 计数单位只能标一个克当量 | 每样食材一个 `grams_per_unit` | 「姜」既有「片」又有「块」，只能按更常见的「片」标定；UI 把这类行标为**估算** |
| 「少许 / 适量 / 几滴」 | 折 3 g / 5 g / 1 ml | 数值保守；同样在 UI 标注**估算** |

**最关键的一条：认不出的单位不做猜测。**
计数单位走白名单（个/根/片/段/瓣/只/粒/块/棵/条/朵/颗），白名单外一律返回「换算不了」，
该行按**未定价**处理并通过 `unpricedCount` 报给前端。
——一个看起来精确、实际漏了半道菜的金额，比一个诚实的「有 3 项未定价」危险得多。

### 9.4 成本不进缓存

`RecipeDetailVO` 里 `favorited` 和 `cost` 是同一类字段：**跟人或跟价走，不能进共享缓存**。
缓存里存 `null`，取出来用 `withCost(...)` 现算复制一份。
如果缓存住成本，管理员改完价后 10 分钟内用户看到的还是旧价，
属于典型的「静默错误」——比直接报错更难发现。

价目本身缓存在 `ingredientPrice`（Caffeine，TTL 10 分钟兜底），
管理端任何写操作都会**整体失效**：价目条目只有一百多条，
整体失效的代价远小于维护精确失效的复杂度。

## 十、冰箱推荐：匹配、降级与取舍

「我的冰箱」要做的事一句话说完：**用户登记冰箱里有什么，系统从现有菜谱里挑出用得上的菜。**
真正难的不是查询，而是**判断两样东西是不是同一个东西**，以及**判断够不够**。

### 10.1 为什么不能只做字符串相等

用户会写「五花肉」，菜谱写的是「带皮五花肉」；用户写「西红柿」，菜谱写「番茄」。
如果只做 `name` 相等，匹配率会低到让功能看起来是坏的——而它其实只是没认出来。

所以匹配是一条三级流水线（`IngredientMatcher`）：

```
① 归一化   去空白 + 拉丁转小写              " 姜 片 " → "姜片"
② 形态剥离 剥掉 末/丝/丁/片/块/段/瓣/碎      "姜片" → "姜"
③ 同义词   收敛到菜谱里常用的写法            "西红柿" → "番茄"
```

然后判三级：**精确 / 近似 / 没有**。近似匹配在 UI 上标「≈」，
让用户自己判断——这和成本模块把估算行标出来是同一个原则：
**宁可展示不确定，也不要悄悄给一个听起来确定的错结论。**

### 10.2 两道护栏：没有它们，结果就不可信

近似匹配天然会误报，两类误报都必须挡掉：

| 护栏 | 挡掉什么 | 为什么必须挡 |
|---|---|---|
| **长度护栏** | 短名只有 1 个字时不参与「包含」匹配 | 否则「葱」会匹配上「洋葱」、「蒜」会匹配上「蒜苗」——这两条恰好都是「有 A 却说能做需要 B 的菜」，是最危险的方向 |
| **加工形态护栏** | 菜谱要「A + 酱/膏/粉/汁/油/苗/芽/精/露/面」时，只有 A 不算命中 | 有番茄不等于有番茄酱，有花生不等于有花生油 |

加工形态护栏是**单向**的：冰箱里有「辣椒面」用来做需要「辣椒」的菜，是合理替代，不拦。
护栏方向搞反就会出现「用户明明有辣椒面，系统却说没有辣椒」这种更让人困惑的错误。

同义词表（`SYNONYM`）只收「换了名字但确实是同一个东西」的组合，初始 20 余条。
它是**烹饪等价表**而不是植物学分类表——「嫩豆腐」和「豆腐」这种包含关系交给近似匹配处理，
不占用同义词表。扩展方式就是加一行，不需要改表结构。

### 10.3 数量判断：复用成本模块的量纲能力，算不出就降级

「有」和「够」是两件事。判断够不够需要的正是成本模块已经解决的那个问题：
**把「2 个」「500 g」「1 斤」放到同一个度量上比较**。

因此这里直接复用，不新写任何换算逻辑：

- 菜谱侧用量 → `AmountParser.parse` → `UnitConverter.toGrams`（克当量来自价目表 `grams_per_unit`）
- 冰箱侧数量 → `UnitConverter.toGrams`
- 两边都拿到克数才比较，得到 `ENOUGH` / `NOT_ENOUGH`；**任何一环算不出来就退化为 `PRESENT`（有就行）**

退化的场景包括：菜谱写「适量/少许」、冰箱没填数量、单位不在白名单、价目表没有该食材的克当量。

**硬约束：`NOT_ENOUGH` 只影响展示与排序，绝不用来排除菜谱。**
宁可多推荐一道并标「量不够」，也不能因为价目表缺一个系数就把本该出现的菜藏起来。

### 10.4 排序：缺主料数是主指标

候选资格是「**至少命中 1 个主料**」。只命中调料的菜谱不算候选——
用户要的是「能吃的菜」，不是「盐管够」。

排序键依次是：

1. 缺几样**主料**（用户最关心）
2. 主料数量不足的有几样
3. 缺几样辅料/调料
4. 用到的**快过期**食材数（降序）——减少浪费
5. 评分、浏览量
6. id（保证结果稳定、可测）

排序逻辑写成纯函数 `RecipeMatcher.ranking(...)`，
匹配写成纯函数 `RecipeMatcher.match(...)`，两者都**不注入 Repository**。
这样这段最需要反复验证的逻辑就能被单元测试直接驱动，
不必为了断言一个排序结果去准备 MySQL 数据——和 `PriceCalculationTest` 测 `UnitConverter` 完全同构。

### 10.5 数据量与演进路径

当前实现是**一次拉平全部菜谱食材行**（30 道菜约 1200 行）再在内存里匹配，
整个请求只有 2~3 次查询。这与随机配餐拉全量候选池的思路一致，在当前数据量下比
「先反查候选 id → 再取详情」的多次往返更快，也避免分步查询之间的一致性问题。

菜谱涨到上万道（几十万行食材）时应该换成倒排路线：

```sql
-- 先按食材名收窄候选（走 idx_ingredient_name），再取这些菜谱的食材
select distinct recipe_id from recipe_ingredient where name in (:matchedNames)
```

这条路径已经在 `RecipeIngredientRepository.findAllRows()` 的注释里标明，
但**不提前实现**——在没有这个量级的数据之前，多写的每一步都是没人验证的复杂度。

### 10.6 为什么不缓存推荐结果

推荐结果同时依赖**冰箱内容**与**用户忌口**，两个输入都随用户操作变化：
缓存命中率低，而失效点分散在冰箱的三个写接口和忌口接口里。
偏偏查询本身只有 2~3 次索引扫描，几百微秒到毫秒级。

用一致性去换这点性能不划算，所以从第一版起就不加缓存。
仅有的复用是忌口关键词缓存（`AvoidanceFilterService`，与随机配餐共用同一份）——
那是**跨用户高度重复**的数据，和「按人按冰箱」的推荐结果不是一回事。
